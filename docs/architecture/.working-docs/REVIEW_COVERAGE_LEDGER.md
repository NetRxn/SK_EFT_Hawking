# Chunked branch review — coverage ledger

**Why this file exists.** The first pr-review-toolkit pass on this branch dispatched all six
agents over the **whole** diff — 451 files, 178k lines of churn. Every agent therefore
*sampled*, and the union of six samples is not a complete review. It read as 100% because
six agents ran; it was not.

**The fix is chunking.** The reviewable surface is partitioned into disjoint chunks small
enough that an agent can read all of its chunk, and coverage is tracked here. The claim
"100% reviewed" is only true when every chunk below is CLOSED.

## The partition

Machine-generated by the packer recorded in `review_chunks.json` (the authoritative list of
which file is in which chunk). Properties **verified at generation**, not asserted:

- every reviewable changed file appears in exactly one chunk — **no overlap, no gap**
- chunk target ≈ 6,000 changed lines; a single file larger than that gets its own chunk

**Excluded as not human-reviewable** (72 files, 84,733 lines): `lean_deps.json`,
`docs/counts.{tex,json}`, `atlas_view.json`, `SURFACE_INVENTORY.md`, `*.pdf`, `*.olean` —
all generated. Excluding them is a claim with a mechanism: each is regenerated by a script
that is itself in a chunk, so the *generator* is reviewed even though the artifact is not.

## Rules given to every chunk reviewer

1. **Review 100% of your chunk.** You are not sampling; that is the failure this replaces.
2. **Reproduce before reporting.** A finding without a command that demonstrates it is not a
   finding.
3. **Commit messages, docstrings and comments are NOT evidence** — they are what you audit.
4. **Read-only.** Restore anything touched; `git status --short` clean before finishing.
5. Report coverage explicitly (files examined, checks verified able-to-fail) so a later
   reader can audit the review itself rather than trusting it.
