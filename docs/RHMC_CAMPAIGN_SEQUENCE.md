# RHMC vestigial campaign — runbook

The single guide to running the HS+RHMC lattice campaign that settles the vestigial-condensate
question. It tells you what the campaign is, how to run each stage, and how to read the result.
Engine internals and the resource profile live in the companion
[`RHMC_MLX_RUNBOOK.md`](RHMC_MLX_RUNBOOK.md); this document is the *what-to-run*.

## The question and the deliverable

Does the auxiliary field `h` develop genuine vestigial (nematic-metric) order that survives the
thermodynamic (L→∞) and chiral (m→0) limits — or is every apparent signal a finite-volume
noise-floor artifact? A defensible answer either way is the deliverable. Concretely, the campaign
is *done* when, across the (L, m) grid, the noise-subtracted order parameters and the
finite-size-scaling discriminants give a consistent verdict:

- **Tetrad order** `tet_m2 = |⟨h⟩_vol|²` compared against its disordered floor `16⟨h²⟩/V`.
- **Nematic-metric order** `Tr Q̃²` compared against a spatially-shuffled floor.
- **FSS discriminants** — connected susceptibility `χ` and the Binder cumulant `U(g)` across L.

`analyze_rhmc_vestigial.py` computes all of these; you never read the raw order-parameter curves
directly (they track `⟨h²⟩ ∝ g²` and rise even in a fully disordered phase).

## Method

**Engine — Hasenbusch(K=1), refined solver, chronological inversion off.** The sampler splits the
fermion determinant `det(M+m²)^½ = det(M+μ²)^½ · det[(M+m²)/(M+μ²)]^½` with the balanced split
`μ² = √(m²·λmax)`, so each factor carries condition number ≈ √(λmax/m²) (~1300 at the reference
point) instead of the full κ ≈ 1.7×10⁶. This mass preconditioning is what makes the campaign
trustworthy: it is exact (the FP64 Metropolis test gives `⟨e^-ΔH⟩ = 1`) and it decorrelates the
order parameter roughly five times faster than the single-pseudofermion sampler — the integrated
autocorrelation time is `τ(tet) ≈ 6–8` versus `≈ 34`. Since the g≥5 region is where any real
signal would first appear and where autocorrelation is worst, that τ reduction is what lifts those
couplings from a handful of independent samples to a publication-grade count.

Chronological inversion (warm-starting the MD force solves) is **off**. It buys a small speedup at
mild masses but softens reversibility enough to bias `⟨e^-ΔH⟩` to ~0.92 in the stiff (small-mass,
high-κ) regime, and it is not validated with the Hasenbusch trajectory. `--hasenbusch` selects the
mass-preconditioned engine with chrono off and its tuned working point automatically; there are no
extra flags to set for the reference mass.

**Certification gate.** Every coupling must hold `⟨e^-ΔH⟩ ≈ 1` (`rhmc_monitor` flags `RED_BIAS`
otherwise). This is the correctness guarantee — a biased point cannot be rescued by more statistics,
so a `RED_BIAS` means stop and diagnose, not run longer.

**Thermalization is cut once.** The driver discards its `--n-therm` trajectories and saves
measurement-only history (recording `n_therm_done` in each npz). The analysis reads that marker and
does not re-cut, so you set thermalization on the driver and analyze with no `--therm` flag. Confirm
equilibration after the fact — the first ~30 saved `<tet>` should show no trend; if they do,
increase `--n-therm` and resume.

**One engine per extrapolation.** The m→0 and L→∞ fits must use data generated by this engine.
Historical Rust/torch nulls corroborate but are not part of the primary dataset — regenerate rather
than mix.

## How to run

Runs launch from the `mlx-hikappa` worktree (which carries the validated engine) and write to the
main checkout's gitignored `data/`. A run is a single GPU-bound process; do not launch parallel
driver processes (they serialize and contend for the one GPU). Use `caffeinate -is` on AC with the
lid open so macOS sleep cannot stall it.

```bash
cd /Users/johnroehm/Programming/PythonEnvironments/Physics/Fluid-Based-Physics-Research/SK_EFT_Hawking/.claude/worktrees/mlx-hikappa
OUT=/Users/johnroehm/Programming/PythonEnvironments/Physics/Fluid-Based-Physics-Research/SK_EFT_Hawking/data/rhmc/L8mlx_m0.05_hasenbusch
caffeinate -is env PYTHONUNBUFFERED=1 uv run --no-sync python scripts/run_rhmc_gpu_production.py \
  --backend mlx --hasenbusch \
  --mass 0.05 --l 8 --replicas 16 \
  --couplings-only 3 4 5 6 8 \
  --n-therm 150 --n-meas 400 \
  --outdir "$OUT" >> "$OUT/run.log" 2>&1 &
```

`--hasenbusch` selects the engine, chrono-off, and the tuned working point (n_md=16, eps=0.031,
hb-n-inner=4) in one flag. `uv run --no-sync` uses the worktree venv as-is (a bare
`uv sync --extra mlx` would drop torch). Every run is checkpoint-resumable: re-running the identical
command reloads each coupling's npz, skips finished couplings, continues a partially-thermalized
chain, and preserves acceptance counters — so it can be started and stopped freely in whatever
chunks the machine's availability allows.

Watch progress with `scripts/rhmc_monitor.py "$OUT"` (add `--watch 300` to poll): expect
`⟨e^-ΔH⟩ ≈ 1.00`, acc ≈ 0.95–0.97, `τ ≈ 6–10`, and per-coupling `RED_NULL` / `GREEN` / `YELLOW`.

## Working points

At fixed trajectory length `τ_traj = eps·n_md ≈ 0.5`, measured at the worst-case coupling g=8
(milder couplings are safer). The fermion force stiffens as m→0, so eps shrinks with mass; never
reuse a lighter-mass step size at a stiffer one. The m=0.05 row is the built-in `--hasenbusch`
default (`resolve_working_point`) — you pass it only to override. For a new (L, m) corner, confirm
acc ≳ 0.90 and `⟨e^-ΔH⟩ ≈ 1` with a short scan first (`scan_rhmc_l8_stepsize.py`).

| mass | `--n-md` | `--eps` | `--hb-n-inner` | acc (g=8) | note |
|---|---|---|---|---|---|
| **0.05** | **16** | **0.031** | **4** | **0.97** | default; measured |
| 0.1 | ~16–20 | ~0.035 | 4 | — | scan before use (less stiff → tolerates ≥ m=0.05 eps) |
| 0.2 | ~16–20 | ~0.04 | 4 | — | scan before use |

`μ²` defaults to the balanced `√(m²·λmax)` per coupling; `--n-poles 24` is a floor that auto-bumps
to hold the heatbath fit (unsigned relerr ≤ 1e-3). Leave both alone.

## Statistics

The driver averages the 16 replicas per trajectory before the autocorrelation analysis, so the
displayed effective sample count is `neff = n_meas / (2τ)` — the replicas sharpen the error bar but
do not raise the displayed neff; τ gates it. At `τ ≈ 7`, `n_meas = 400` gives `neff ≈ 28`, well past
the threshold where the monitor trusts the τ estimate and the noise-floor comparison. This is why
the engine's τ reduction, not raw per-trajectory speed, is the thing that makes the null credible.

## The sequence

Each phase writes to `data/rhmc/L{L}mlx_m{mass}` (or an explicit `--outdir`) and ends in an analysis
gate that decides whether to proceed, expand, or ship.

**Phase 1 — reference null: L=8, m=0.05.** The literature-grade starting point; couplings
g = 3,4,5,6,8, weighted to high-g. Use the command above.
*Gate:* `analyze_rhmc_vestigial.py "$OUT"` — both channels at floor (ratio ≈ 1) and χ flat means the
null holds at the reference point; a significant floor-excess means a candidate signal, so densify
couplings around it and add statistics before believing it.

**Phase 2 — mass axis: L=8, add m=0.1 and m=0.2.** Completes the chiral axis; m→0 is the deliverable
(the γ5 mass is a chiral regulator). Scan each mass's working point first, then run the same
couplings.
*Gate:* `analyze_rhmc_vestigial.py data/rhmc/L8mlx_m0.05 …_m0.1 …_m0.2` — the m→0 extrapolation of
the noise-subtracted order parameters. Extrapolating to floor means no condensate in the chiral
limit at L=8; extrapolating above floor escalates to Phase 3 on the surviving couplings.

**Phase 3 — volume axis (FSS): L=10, 12 at m=0.05, matched couplings.** The thermodynamic-limit test;
run the same couplings at larger L so the Binder cumulants are comparable. Cost grows ∝ L⁴ (≈ 2.9
min/traj at L=10, ≈ 6 min/traj at L=12 on the Mac).
*Gate:* the analysis's FSS block — χ growing/peaking as V↑, or Binder curves crossing across
L=8/10/12, means a real transition (expand the grid around it); flat χ with no crossing ships the
null and makes Phase 4 unnecessary. A single-L Binder ≈ 0.6 is the disordered baseline, not order.

**Phase 4 — only if a signal survives Phases 2–3.** Densify couplings around the candidate
transition, add L and possibly smaller m, and concentrate statistics where τ has grown (critical
slowing is worst exactly at a transition). Its scope is defined by the gates above; if those are
null, there is no Phase 4.

## Open areas for re-evaluation

- **Larger volumes and the 3090.** Cost grows ∝ L⁴; L=12 is a multi-day run. The fused Metal hop
  kernel is Metal-only, so on CUDA the engine falls back to the slower einsum path — the 3090's
  per-trajectory advantage is not realized until a CUDA kernel exists, and the CUDA path must be
  parity-checked (`validate_cuda_rhmc.py`) before its results are trusted, since Metal is FP32-only
  and the refined solver's precision seam behaves differently on native-FP64 hardware.
- **Solver envelope.** Deflation of the heatbath's low-mode tail is not implemented, so the current
  practical envelope is L ≤ 12, m ≥ 0.05. L=16 or smaller masses need solver work first.
- **Critical slowing at a transition.** If the FSS gate fires, τ spikes where the physics is;
  Hasenbusch helps but may not fully cure it — budget extra statistics there.
- **Per-corner working points.** Each new (L, m) needs its own short acc / `⟨e^-ΔH⟩` scan; the
  lighter-mass entries in the working-point table are estimates pending measurement.
- **τ-reduction rigor.** The ~5× autocorrelation reduction is measured against the single-PF
  engine's estimator on a separate run. A matched single-PF chrono-off arm from the same
  configuration (~2.7 h, identical estimator) would turn it into a referee-proof number. Not
  required to run the campaign; worth it for the methods write-up.
- **κ-gate merge.** The safe chrono default for the *single-PF* engine lives on the
  `mlx-rhmc-hikappa-chrono` branch. Until it merges, a single-PF run from `main` at m ≤ 0.05 needs
  an explicit `--no-chrono`. The Hasenbusch path used by this campaign is unaffected.
