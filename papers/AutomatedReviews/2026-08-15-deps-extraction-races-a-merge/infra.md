# A backgrounded deps extraction reverted a merged regeneration, then certified it fresh

## Summary

**1 MAJOR.** `scripts/extract_lean_deps.py` reads the built `.lake` oleans and writes
`lean/lean_deps.json` plus a hash **over the `.lean` sources**. Those are two different clocks,
and nothing serialises the writer against anything else.

Observed 2026-08-15, on the lead's own machine:

1. `lake build SKEFTHawking.ExtractDeps` ran on `main`, whose Lean sources were the
   *pre*-heat-kernel-correction ones.
2. `extract_lean_deps.py` was started in the background against that build.
3. **`redraft/D3` merged while it ran**, bringing corrected Lean sources *and* a correctly
   regenerated `lean_deps.json` (40 774 declarations, cross-checked by its author: all ten
   renamed/new names present, all four old names absent).
4. The background extraction finished and wrote **40 769** over it — the pre-correction
   substrate — and stamped a hash computed over the **post-merge sources**.
5. Re-running the extractor then reported **"already fresh — no extraction run."**

So the artifact described the old substrate, the hash asserted it matched the new sources, and
the tool's own freshness check agreed. Recovered with `git checkout --` and re-verified by
name presence/absence, not by count.

### Why this is worse than a stale file

A stale artifact that *knows* it is stale gets regenerated by the next consumer. This one
**certifies itself fresh**, so every downstream consumer — `formula_grounding`,
`bundle_apex_resolves`, the graph build, the atlas — reads the pre-correction substrate and
passes. The heat-kernel correction renamed `a4_alpha_neg` to `a4_alpha_eq_zero` because the
old statement became FALSE; a consumer resolving against the reverted file would have found
the false theorem and reported green.

### 1.1 — 🔴 MAJOR — the extractor writes a source-derived hash for olean-derived content

- **Severity:** major
- **Lane:** `infra`
- **Verify:** `cd "$REPO" && uv run python -m pytest tests/ -q -k "extract_lean_deps and (stale or olean or race or lock)"`
  *What it asserts:* that a test pins the extractor against writing a source-hash for content
  read from an older build. Exits 1 at HEAD — no such test exists.
- **Gate:** SubstrateIntegrity
- **Location:** `scripts/extract_lean_deps.py` — the write path and `compute_lean_hash`
- **Observed:** freshness is keyed on `.lean` source content; the payload comes from `.lake`
  oleans. A run that spans a source change silently pairs new-hash with old-content.
- **Evidence:** measured 2026-08-15 as above; `lean_deps.json` went 40 774 → 40 769 across a
  merge and the extractor then reported "already fresh".
- **Expected:** the hash covers what the payload was actually derived from, or the extractor
  refuses to write when the sources moved under it.
- **Fix:** stamp the **build** the extraction read (olean mtimes / a `.lake` manifest hash)
  alongside the source hash, and refuse to write if the source hash at completion differs from
  the one at start — the read-back-after-write discipline `scripts/close_finding.py` already
  uses. ⚠️ **Do NOT fix this by deleting `lean_deps.json.hash` to force a refresh** — that is a
  separately-recorded no-go; run the extractor, do not defeat its cache.
- **Related:** identical shape to `2026-08-15-seeded-mutation-seeder-vs-seeder-race` — two
  writers, each internally correct, no serialisation between them, and the loser's state
  survives looking valid. That one was fixed with a per-path lock; this one is a *derived
  artifact* rather than a production file, so the lock is not the same lock.
- **Cache:** N/A.
