- **Gate:** NarrativeGrounding (tooling)
- **Location:** `scripts/validate.py`, `_strings_in`'s `nums > 8 and nums == len(obj)` branch
- **Observed:** The docstring justifies the exclusion as protecting against "hundreds of floats whose
  low-order digits move with library versions". **Measured, the exclusion never fires on D11 and the
  jitter exposure it targets is unmitigated.**
- **Evidence:** Instrumented count over both bundle notebooks' stored plotly payloads:
  ```
  D11: base64 bdata arrays=24   plain numeric lists=354   SKIPPED by the >8 rule=0   scalars=675
  D12: base64 bdata arrays=32   plain numeric lists=276   SKIPPED by the >8 rule=2   scalars=554
  ```
  Plotly serializes numpy arrays as `{"bdata": "<base64>", "dtype": …}`. `bdata` is a **string**, so it
  takes the string branch and is compared byte-for-byte; only arrays that happen to be plain Python
  lists reach the `>8` rule. So the discriminator is "was this a numpy array or a list at the call
  site", which is an implementation accident, not a claim/non-claim distinction. Consequences measured
  in both directions:
  - **Jitter is fully exposed.** Multiplying one 400-point bulk curve by `(1 + 1e-15)` — the textbook
    non-claim — FAILS the check: `stored='AAAAAAAA8D/D6wr2ag/wPzmM…' fresh='BQAAAAAA8D/I6wr2ag/wPz6M…'`.
    A plotly or numpy version bump can fire the check on all 56 base64 arrays across both notebooks.
  - **Direct answer to the ask — can a claim hide in a skipped array?** Not today. The only two skipped
    arrays are `D12` cell 14 `data[0].y` and `data[1].y`, both 400-point plotted curves, correctly
    excluded. But that is luck: moving any `np.linspace(...)` to a list comprehension silently
    demotes an array from "compared byte-for-byte" to "length only".
- **Fix:** decode `{bdata, dtype}` dicts and route them through the *same* rule as plain lists, then
  apply one consistent policy to both — e.g. compare `len` plus a checksum of the values rounded to a
  fixed number of significant digits. That kills the jitter fragility and removes the numpy/list
  asymmetry in one change.

**qi-a-gate-written-from-one-finding-inherits-that-finding-s-scope.** Three of this round's REQUIRED
findings (1.1, 4.2, 5.1) share a shape: a new gate was written to close a specific finding, closes it
correctly and verifiably, and leaves the adjacent surface of the same failure class unguarded — the
citation content gate stays opt-in and never learned venue fields; the metadata guard fixes the counts
but not the verdict fields those counts justify; the notebook gate compares text and scalars but
discriminates bulk arrays by an implementation accident. In each case the gate's own docstring
correctly narrates the finding it was born from, which is what makes the residual hard to see: the
gate reads as complete because its motivating story is complete. Recommend that a gate authored in
response to a Stage-13 finding ship with an explicit **negative test list** — two or three mutations
the author expects it to catch *and* two the author knowingly leaves out, recorded in the docstring —
so the uncovered surface is a stated scope rather than an assumed one. Cheap evidence that this works:
every hole in this round's three findings was found by a mutation test that took under a minute, and
the author had already run the positive half of exactly that test.

**qi-verification-records-must-quote-the-request-not-just-the-response.** Round 7's cache files
recorded "volume and page are NOT in the API response" as a fact about the source, when the true
